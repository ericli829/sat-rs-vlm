# 云端全流程对接与分析报告

## 1. 工程和实验边界

当前工程目录：

```text
team/sat-rs-vlm
```

正式分支：

```text
lyz-reliability-v15-migration
```

本报告覆盖的是参数级单粒子翻转（SEU）敏感性分析和软件保护流程：

```text
模型加载
  -> clean 基线推理
  -> 指定层/模块/bit 注入
  -> fault 推理
  -> clean/fault 配对比较
  -> 敏感性绘图
  -> 自动风险分级
  -> 分级保护建议
```

KV Cache 和激活值不是持久化参数，不能直接套用参数 bit flip；当前工程对激活提供 `ActivationGuard` 检测，KV Cache 自动回滚仍属于后续运行时实验。

## 2. 云端必须准备的文件

### 模型

需要一个完整的本地 Qwen3-VL 模型目录，例如：

```text
/root/autodl-tmp/models/Qwen3-VL-2B-Instruct/
├── config.json
├── model.safetensors 或分片 safetensors
├── tokenizer.json / tokenizer_config.json
├── preprocessor_config.json
└── chat_template.json
```

### Adapter

正式 v1.5 默认配置要求 Adapter：

```text
/root/autodl-tmp/outputs/training/lora_baseline/best_adapter/
├── adapter_model.safetensors
├── adapter_config.json
└── processor/ 或对应处理器文件
```

Adapter 会参与正常推理，也会作为默认故障目标扫描。没有 Adapter 时只能进行 base-model 验证，不能作为正式 LoRA 结果。

### 数据集和评测清单

数据根目录需要包含图片和可靠性评测 JSONL：

```text
/root/autodl-tmp/datasets/VRSBench/
/root/autodl-tmp/sat-rs-vlm/data/processed/qwen3vl_val.jsonl
```

JSONL 中的图片相对路径必须能在 `image_root` 下解析。若没有可靠性评测清单，先使用仓库中的数据清单脚本构建固定样本集。

## 4. 运行前检查

### 4.1 一键预检、对齐和计划校验

```bash
python scripts/reliability/cloud_preflight.py \
  --environment autodl \
  --config configs/reliability/experiments/v15_sensitivity.yaml \
  --output reports/reliability/cloud_preflight.json
```

必须确认以下项目全部存在：

- base model
- processor
- Adapter
- dataset root
- reliability eval manifest
- CUDA

该命令一次完成路径、CUDA、真实 safetensors 参数名、selector 命中、dtype、层号和条件计划检查。只有 `passed: true` 才继续。

### 4.2 查看条件计划（可选）

```bash
python scripts/reliability/run_v15_sensitivity.py \
  --environment autodl \
  --config configs/reliability/experiments/v15_sensitivity.yaml \
  --run-id v15-full-scan \
  --dry-run
```

默认 Qwen3-VL 2B 配置计划为 3078 条条件，口径是：

- language model、Attention、MLP、Vision encoder、Embedding、LoRA Adapter；
- 语言模型第 0 到第 27 层；
- sign、exponent、mantissa；
- 1、10、100 bit；
- 每个条件 3 次重复。

如果 dry-run 数量不是预期值，先检查配置，不要启动全量扫描。

### 非 2B 模型适配

云端模型不要求必须是 Qwen3-VL-2B。更换模型时至少同步修改：

```yaml
model:
  base_model: /path/to/actual-model
  processor_id: /path/to/actual-model
  adapter_path: /path/to/matching-adapter
fault:
  layer_indices: auto
```

`layer_indices: auto` 会从实际 safetensors 参数名中发现 `layers.N` 或 `blocks.N`，不再假定只有 28 层。发现结果会写入 `config_resolved.yaml` 和 `condition_plan.json`。如果模型使用非标准命名，先运行参数清单并手动填写层号：

```bash
python scripts/reliability/verify_model_selector_alignment.py \
  --model /path/to/actual-model/model.safetensors \
  --output <RUN_DIR>/selector_alignment.json
```

不同模型的 Attention/MLP/视觉模块名称可能不同。必须检查参数清单中的实际命名是否能被 selector 命中；不能命中时应增加对应 selector，而不是直接启动全量扫描。模型 dtype 也必须以真实权重为准，不能把 2B 模型的 BF16 bit 范围直接套到其他 dtype。

## 5. 真实 GPU 单点验证

```bash
  --config <resolved-eval-config.yaml> \
  --output-dir <run-dir>/smoke_mlp_l14 \
  --fault-target mlp \
  --fault-layers 14 \
  --fault-num-bits 1 \
  --fault-bit-plane exponent \
  --fault-seed 20260822

# Vision encoder
python scripts/reliability/run_fault_evaluation.py \
  --config <resolved-eval-config.yaml> \
  --output-dir <run-dir>/smoke_vision \
```

每个输出目录都必须包含：


并且 `actual_bit_flips` 必须等于计划翻转数。若使用 `--activation-guard`，检测到异常时命令阻断是预期的保护行为，不代表注入失败。

## 6. 启动完整扫描

单点验证通过后启动：

```bash
python scripts/reliability/run_v15_sensitivity.py \
  --environment autodl \
  --config configs/reliability/experiments/v15_sensitivity.yaml \
  --run-id v15-full-scan \
  --activation-guard
```

中断或节点重启后使用同一个 run id：

```bash
python scripts/reliability/run_v15_sensitivity.py \
  --environment autodl \
  --config configs/reliability/experiments/v15_sensitivity.yaml \
  --run-id v15-full-scan \

```

`--resume` 会跳过完整条件，只重跑缺失、失败或结构不完整的条件。不要修改已有 run 的 condition plan；若要改变样本数、seed 或目标集合，使用新的 run id。

## 9. 自动风险分级

对真实扫描结果生成保护等级：

```bash
python scripts/reliability/build_risk_policy.py \
  --sensitivity-root <OUTPUT_ROOT>/reliability/v15_sensitivity/v15-full-scan \
  --output <OUTPUT_ROOT>/reliability/v15_sensitivity/v15-full-scan/protection/risk_policy.json
```

默认规则：

```text
critical: invalid >= 0.20 或指标下降 >= 0.20 或 changed >= 0.80
high:     invalid >= 0.05 或指标下降 >= 0.08 或 changed >= 0.40
medium:   invalid > 0 或指标下降 >= 0.02 或 changed >= 0.10
low:      其他情况
```

风险报告会同时列出：

- target、层号、bit-plane；
- 观测到的 changed/invalid/quality drop；
- 推荐的软件保护；
- 需要平台硬件配合的动作。

## 10. 分级保护解释

### Low

监控、记录 fault metadata。适合输出变化小、无非法输出的条件。

### Medium

在监控基础上启用输出校验、重试和当前步骤局部重算。

### High

增加 SHA-256 manifest、热备副本、可信副本和定期 scrub。

### Critical

执行故障阻断、回滚和可信副本恢复；ECC、双执行检测和 TMR 需要平台级实现，软件报告不能宣称已经提供这些硬件能力。

## 11. 保护策略实验

保护策略结果必须与同一批 fault 输出配对，避免重复推理。报告至少应记录：

- 无保护输出变化率；
- 输出校验/投票后的有效率；
- 重试或局部重算恢复率；
- trusted copy 恢复率；
- 额外延迟、存储和计算成本。

## 12. 常见故障处理

### Adapter 未命中

先用参数清单检查真实名称：

```bash
python scripts/reliability/build_fault_inventory.py \
  --adapter <ADAPTER_DIR_OR_FILE> \
  --output <RUN_DIR>/adapter_inventory.json
```

### 条件数量不对

重新执行 `--dry-run`，检查 targets、layers、bit counts、repeats 和 bit planes。

### comparison 失败

检查比较输出是否位于允许的结果目录之外，并确认 baseline 和 candidate 的 `evaluation_v1_5/metrics.json` 都存在。

### ActivationGuard 阻断

这是 fail-closed 行为。保留 guard 报告，同时在需要记录未保护 fault 影响时关闭 guard 单独重跑；两类结果不能混为一个结论。

### OOM

先降低 `max_eval_samples`、`eval_batch_size` 和 `max_new_tokens`，不要改变 condition plan；正式扫描应使用新的 run id。

## 13. 结果可信边界

只有满足以下条件的结果才能用于正式敏感性结论：

- GPU 真实推理；
- 正式模型和 Adapter；
- 统一数据清单；
- 多个 seed；
- 足够样本量；
- clean/fault 成对比较；
- 完整记录参数名、层号、投影、bit-plane、bit index 和运行成本。

本地 CPU、单样本或 fixture 结果只能证明流程，不代表正式鲁棒性结论。
