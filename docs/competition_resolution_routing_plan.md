# 开发图片集分析与分辨率路由方案（待实施）

2026-10-03，按用户要求修订：入口路由只判断分辨率和图像数量，题意由 planner 处理；
双时相统一走现有低分辨率模型。本文是待实施方案，没有修改实际路由代码。

## 开发包分析

来源：[ModelScope masonJ/rsu-dev100-v2-images](https://www.modelscope.cn/datasets/masonJ/rsu-dev100-v2-images)。
包格式 `rsu-sealed-images-v1`，`dataset_id=rsu-dev100-v2`。
下载压缩包 1,558,394,526 字节，SHA-256：
`5d4d976e8d6c6a04ab68a537f2de3cb4911922876cc1e628f8f87612a606a1df`。
压缩包校验和与官方 sidecar 一致，125 张资产的大小、SHA-256、MIME、实际图像格式均校验通过。
现有 `ImagePackage` 也成功读取全部资产，没有修改、重命名或重新编码原文件。

| 原图尺寸 | 图片数 | 原生检测分块数* |
|---|---:|---:|
| 256×256 | 50 | 1 |
| 512×512 | 25 | 1 |
| 1565×1903 | 1 | 4 |
| 4096×4096 | 11 | 16 |
| 4097×4096 | 11 | 16 |
| 4096×4097 | 1 | 16 |
| 5616×3744 | 3 | 20 |
| 7360×4912 | 23 | 35 |

\* 直接调用现有 `generate_tiles(width, height, 1333, 0.15)` 得到，不包括检索、细化、重试或其他尺度。
这是处理量估计，不能推导真实 GPU 推理时间或准确率。

100 张实际 PNG、25 张实际 JPEG，全部 RGB；资产没有扩展名，模型必须按内容解码。
75 张不超过 512×512，1 张约 298 万像素，49 张约 1678–3615 万像素。
原图最长边中位数 512、75 分位数 4097、90 分位数 7360；最大长宽比约 1.50。

原始资产合计 1,558,349,746 字节；压缩包与解压目录同时保留合计约 3.12 GB。
最大 PNG 文件约 81.3 MB；最大原图解码为 RGB 约 108.5 MB。
125 张全部解码的 RGB 理论总量约 3.88 GB，这不等于服务常驻内存；数组、复制、float32 张量和缓存还会增加开销。
避免预解码全部图片、为全部原图永久生成 BMP，或将原图/所有 tiles 一次搬到 GPU。

图片包 README 明确：125 张图片对应网站 100 道题，但不含题干、答案、金标和题目到图片映射。
仅凭该 manifest 不能确认计数/定位/变化题数量、准确率、时序配对或数据集来源。
后续文件 SHA-256 比对可以确认与本地数据集完全相同的图片，结果仅用于来源验证，
不把文件 ID、哈希、数据集名称或题意加入入口路由。

在指定 Python 3.11.9 下，现有 `ImagePackage` 首次全包校验 4.276 秒，缓存后全包重复校验 0.050 秒。
这是本机文件缓存条件下的哈希/格式验证时间，不包含完整 RGB 解码、BMP 转换、模型推理和 HTTP 网络时间。
首次真实请求的该项时间仍须计入端到端预算。

## LEVIR-CC 来源验证

按用户提供的本地 LEVIR-CC 目录扫描 22,326 张图片，共约 2.69 GB。
先比较文件长度，22,263 个文件长度与开发包所有资产均不同，不可能是相同字节文件；
对剩余 63 个候选计算原始文件 SHA-256，实际读取约 8.02 MB。
这种预筛不会漏掉字节完全相同的文件，扫描和哈希共约 2.83 秒，无读取错误。

| 验证项 | 结果 |
|---|---:|
| 开发资产精确匹配数 | 50 / 125 |
| 匹配图片尺寸 | 全部 256×256 |
| 本地匹配文件数 | 50 |
| 两侧均匹配的 A/B 时相对 | 25 |
| train / val / test 匹配图片数 | 30 / 12 / 8 |
| 未匹配的开发资产数 | 75 |

因此，开发包全部 50 张 256×256 图片与本地 LEVIR-CC 中的文件字节完全一致；
可以按源目录 A/B 角色及同名图片组成 25 组完整时相对。
另对这 50 个开发资产重新计算 SHA-256，全部与对应本地源文件的哈希一致。
这证实 LEVIR-CC 图片来源，但不能据此确认剩余图片来自另外三个数据集，
也不能断言网站一定按这 25 组分配题目、问题内容或正确答案。
没有读取 captions、annotations 或金标；不根据源目录重新排序在线请求中的 images。
SHA-256 未命中也不能排除重编码、裁剪或其他变换后的同源图片。
剩余 75 张在尺寸/编码上恰分为 25 张 512×512 PNG、25 张其他尺寸 JPEG、25 张大尺寸 PNG。
该分布与四组抽样的假设相容，但编码/尺寸分组不构成其余三个数据集的来源证明。
逐图清单与成对关系保存为本地分析目录下的
`levir_cc_sha256_matches.csv`、`levir_cc_sha256_pairs.json` 和 `levir_cc_sha256_summary.json`。

## 职责边界与当前代码

旧 `taskgraph/routing.py` 的 `DatasetExecutionPolicy` 按数据集和任务匹配：
VRSBench/LEVIR_CC 默认 `DIRECT_VLM`，MME/XLRS 默认 `TASKGRAPH_UHR`。
比赛 `competition/protocol_v2/adapter.py` 已经绕开这些 benchmark 默认值：
按答案合同、题意和图像数量显式设置执行模式，不依赖请求中的 dataset 标签。
目前两条链路都没有通用的分辨率预算策略。

目标职责明确分为三层：

1. **入口路由**只读取已校验的图像数量、实际宽高，选择低分辨率模型或 planner/UHR 路径。
   不接收 question、答案类型/选项、dataset、asset ID/hash 或语义 intent。
2. **planner**在被选择的 UHR 路径内解析题意、选择算子、搜索范围和所需证据。
   大图的场景描述、小目标计数、关系和路径可以产生不同计划，由 planner 负责这些差异。
   低分辨率/双时相路线沿用原直接模型回答，不为路由额外调用 planner。
3. **答案处理**使用 response_constraint 选择有限候选评分、严格整数/JSON 解析、坐标换算及序列化。
   答案合同约束输出，不改变已经选定的模型路线。

后续需要删除比赛 adapter 的 `_SIMPLE_COUNT`、`_COMPLEX` 题意正则、
按 bbox/integer 约束切换模式的分支，以及入口从问题中抽取 target_category 的逻辑。
task_category 只保留该图像路线的中性标记，不能用于第二次语义/数据集路由。
旧 benchmark 路由可以保留兼容开关，比赛入口显式 execution_mode 优先。

## 候选分辨率规则与双时相优先级

以下仅为依据本包分布提出的配置候选值，尚未通过真实题目和模型效果标定：

| 优先级 | 候选条件 | 路线 | 说明 |
|---|---|---|---|
| 1 | 两张图，尺寸不限 | DIRECT_VLM / 现有 semantic_2b | 双时相优先于任何尺寸阈值 |
| 2 | 单图，最长边 ≤ 1024 | DIRECT_VLM / 现有 semantic_2b | 本包 75 张图片满足该尺寸条件 |
| 3 | 单图，最长边 > 1024 | TASKGRAPH_UHR / 原 planner 与 providers | 本包其余 50 张图片满足该尺寸条件 |

这是两条模型路径，不必再增加一个 medium 模型或按题意选择 DIRECT_DETECTION。
1565×1903 的一张中等图也进入 UHR，由 planner 处理；原生检测若被计划使用，仅有 4 个 tiles。
4096、4097 在同一路线，避免一像素导致模式变化；新阈值边界测试应覆盖 1023/1024/1025。
阈值 1024 为配置候选值；已知本包的两簇之间没有 513–1564 最长边图片，
但仍应以现有模型训练分辨率与真实结果校准，不将来源匹配转成数据集路由规则。
以上 75/50 是图片尺寸数量，不是 100 道题的路由数量。

双时相训练未覆盖 UHR planner 计划，首版所有双图直接进入已有低分辨率语义模型，
包括两张大图和大小混合双图，不因 bbox/integer/关键词改走 UHR。
严格使用请求 images 顺序（before、after）；SHA 匹配得到的本地 A/B 关系只用于离线来源报告。
记录各图宽高及总视觉 token 预算，使用现有 processor 对输入降采样，保持当前显存预算。
不生成双时相 UHR 切片/变化检测计划，不增加模型实例或 GPU 并行。
目前确认的 25 组源图均为 256×256，支持这一首版选择；不能据此保证以后不会出现大图变化题。
若以后出现双时相大图，当前路线仍按规则执行，其细小变化效果需独立评估，再考虑专门训练。

当前 semantic_2b 配置 `max_pixels=409600`。仅按面积等比缩放估算：
4096×4096 缩放系数约 0.1562，7360×4912 约 0.1064；原图 10 像素目标可能缩到约 1–2 像素。
实际 processor 还涉及尺寸取整、patch 和视觉 token 计算，须用真实 processor 统计。
大图单图进入 planner 后，保留局部证据、是否切片和是否只用 overview 都由计划决定。
双图的视觉 token 与 KV 开销通常叠加，必须用实际 token 数和峰值显存校准总预算。

## 输出能力补齐，不参与路由

低分辨率直接计数/grounding 在旧 VRSBench 路线中已有路径，但比赛路线尚不能直接套用：
目前比赛 `defer_final_answer=True` 的 DIRECT_VLM 交接 ImageRef，bbox resolver 需要 Region/严格 JSON Answer，
integer resolver 需要 ScalarInt。仅改 mode 会造成答案类型不匹配。
后续必须增加复用现有训练提示的结构化证据产生路径：计数严格解析 `{"count":...}`，
grounding 严格解析单个 `{"label":...,"bbox":[...]}`，附带明确坐标制、原图/裁剪参考系和图像索引。
保持整数/有限答案校验，不用自由推理正则抽取、不用假的 0 或任选框兜底。
本次只完成 bbox 格式转换，没有增加这些直接生成路径或修改路由。

后续按答案合同调用同一已选模型的对应训练提示/评分，不能因此切换执行模式。
例如低分辨率 integer 从同一 semantic_2b 的合法计数 JSON 产生 ScalarInt；
bbox 从同一模型的严格 grounding JSON 产生原图像素框，坐标制与所属图像明确。
双图 bbox 应依据协议已明确的目标帧设置 image_index；不明确时仍报错，不猜 before/after。
单选和 enum 复用有限候选评分，原有选项标识与顺序不变。
入口不需要语义 intent 分类器；中文、否定、关系与比较语义只在所选模型/planner 中理解。

## 坐标合同

现有训练 `data/prompt_templates.py` 明确要求 grounding 输出 normalized_0_1 xyxy JSON，
原检测/几何适配器的 Region 通常已经是原图全局像素。
比赛输出统一为原图像素 `[x1,y1,x2,y2]`，保留浮点精度，不用数值范围猜格式。

本次新增的显式换算支持 0–1、0–1000、百分比、像素及明确的 cxcywh。
原图归一化 xyxy：`[x1*W,y1*H,x2*W,y2*H]`；
裁剪归一化先乘裁剪宽高，再加原图裁剪左上角，必须有有效 `reference_bbox_xyxy_global`。
typed global Region 默认保持像素；只有模型 JSON 未声明格式时才可使用配置中的训练坐标格式。
双图模型输出需明确 `image_index`，最终图像尺寸必须符合 bbox 合同。
拒绝范围未知、非数、越界、面积非正、多个框、自由推理文本及缺少参考系的 crop-local 结果。
转换来源与结果只保存在内部 trace，外部仍只返回协议规定字段。

## 显存、CPU、磁盘和时间预算

复用现有模型和单 HTTP worker；不通过增加 GPU worker、模型实例、batch 或 GPU 预取实现路由加速。
CPU 继续使用现有有界预取：每个现有检测 worker 最多预备一个后续 tile，COUNT 沿用串行 GPU 执行。
候选框与原图解码缓存保持有界，完成后释放；ROI 的数量、像素预算与保留周期应可记录。
PNG/JPEG 解码、裁剪/BMP 写入、worker 读图/processor、推理、检索、NMS/COUNT、答案转换都计入端到端。
原图无需永久转 BMP；现有按需 BMP 是内部 tile 传输，不改变 manifest 资产。
磁盘吞吐已经可能成为瓶颈时，增加 CPU 预取深度未必提速，应同时观测读写量和 CPU 空闲时间。

先记录当前检测 worker 的实际常驻/峰值显存，再标定总视觉 token、ROI 数和预算。
现有 runtime 示例中 `parallel_workers` 写了两次，YAML 最后一个值是 5，
且注释说明峰值已接近约 32 GB 边界；因此不能把示例当作本机显存安全保证。
本次保留该配置，后续单独评估生产硬件允许的现有 worker 数和预留显存，不增加它们。
planner/Route-4B 的实例复用和权重常驻情况也应以 provider inventory 与显存实测确认。

在已选的 UHR 路径内，planner 可计划 overview、局部检索/细化或完整扫描。
不通过入口题意分支优化这些阶段；需要全图计数的计划仍须保留覆盖和去重语义。
可配置 max_visual_tokens_total、max_roi_count、CPU 预取/缓存上限和请求剩余时间，
这些是资源策略，不能混入纯答案 AnswerContract。
在已有 120 秒 HTTP 预算内估计各阶段成本，并预留最终评分/序列化时间。
能力不足、超时或资源不足时使用现有显式错误；超时后保持 GPU 忙锁直到实际执行结束，避免下一题叠加显存。
不能通过耗尽预算后返回任意合法答案掩盖失败。

## 分阶段实施与验证

1. 新增纯函数 ImageProfile/RouteDecision 与可配置分辨率策略，先以 observation/shadow 模式记录建议，
   不改变当前执行路线。路由函数输入只有已校验的图片尺寸/数量及固定分辨率阈值。
   RouteDecision 单独记录 mode、尺寸、双时相优先/尺寸阈值理由；不包含题意、合同或来源标签。
2. 增加直接结构化计数/grounding 证据产生能力，复用现有训练提示和模型实例；
   本次已完成的坐标转换作为统一出口。未知格式与多框仍失败。
3. 在开发请求或人工构造的代理问题上比较当前路线与候选路线。
   原始图片包本身没有真题/金标，代理问题只验证工程和资源边界，不能称为开发集得分。
   实际模型测试只用本地已保存模型及开发图片，分别统计首次/暖机后延迟，完整记录预处理/BMP 成本。
4. 观察答案合法率、超时/OOM、端到端 P50/P95、各阶段时间、CPU/磁盘读写量、峰值内存/显存、检测覆盖。
   真实准确率通过获授权的平台 smoke/full 验证；本次没有注册接口或发起网站评测。
5. 通过后再启用新比赛策略。旧 benchmark 保留兼容开关，避免同时改变历史实验默认路由。
   显式 RuntimeRequest.execution_mode 优先；启用新策略时由策略决策，其余仍走旧 dataset policy。

必须覆盖的边界：1023/1024/1025 与 4095/4096/4097 尺寸变化；等比例缩放后的像素 bbox；
单图小尺寸/单图大尺寸、两图小尺寸/两图大尺寸/大小混合；交换 before-after 不改变 route，但保留输入角色顺序。
相同尺寸/数量下，更换问题、语言、否定/关系/计数/路径关键词、答案约束/选项不应改变 route。
更换合法 manifest 的 dataset_id 或重新封装合法资产 ID/hash，不应改变相同尺寸/数量请求的路线。
不同题意是否产生不同 UHR 计划由 planner 测试验证；小像素框不误判归一化，crop offset 只换算一次。
测试生产 mock/fake 禁止、HTTP 答案合同、任意 choice ID、旧 benchmark 路由兼容与资源超时锁。

当前结论：入口仅按图像数量和分辨率选择路径，双时相优先走低分辨率模型，
单张大图交给 planner 决定后续处理；来源匹配是离线证据，不参与 route。
实际修改仍需接通低分辨率结构化输出并验证模型效果和峰值显存。本次保持路由代码未修改。
